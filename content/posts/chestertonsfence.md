Chesterton's fence is "the principle that reforms should not be made until the reasoning behind the existing state of affairs is understood." [Wikipedia](https://en.wikipedia.org/wiki/G._K._Chesterton). In software development think about is as don't change code or an architecture before you understand why it is the way it is. 

This is a good principle but I also started thinking about it from another perspective. When looking at an existing solution we as software engineers and developers can be very critical, this is not good, we have better ways to solve these kind of problems, let's migrate, use a new technology. Yes we could probably improve the solution, the industry changes fast. But don't forget to be proud! The solution is there, adds value, sometimes it has been doing that for a long time. Give it a chance and remember that when it was designed the decision were based on other requirements and possibilities than you have today. And this can help your reason. Do you really need to change it? Are the requirements that different now? Is this a dinosaur or could it be a [technological shark](https://www.simplethread.com/relational-databases-arent-dinosaurs-theyre-sharks/) that still is a good way to solve the problem?
